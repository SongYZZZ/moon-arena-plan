# MoonArenaPlan 0.1.0 终审自查（2026-11-01）

## 总体判断

按 osc2026-guide 的终审模式检查本地仓库，并结合用户提供的十月九项验收指南。当前 schema 1 声明范围已实现，工程交付项有可复现证据；代码错误已完成修复及回归。此结论不是组委会审核或获奖保证。报名提交不在当前任务范围。

项目是独立新建的静态多内存区规划与核验工具。价值边界是调用方已给出准确字节数、串行时序和访问限制的场景；没有把静态合同验证写成真实板卡部署、完整推理框架或整机 RAM 保证。

## 已发现并修复

- 精确数值输入：统一 Int64 字段的十进制字符串表示，并验证真正的 CLI 输入和嵌套可选固定字段往返。
- 约束静默遗漏：严格拒绝未知字段及重复 JSON 键，避免拼错字段时约束被忽略。
- 小数时间步截断：在类型转换前拒绝小数和指数数值 token。
- 排序定义：对 schema ASCII 标识符使用显式字典序，避免依赖底层字符串比较顺序。
- 诊断放大：对抗布局可能产生二次数量的重叠诊断；修复前新回归用例失败，修复后限定 4096 条并返回 FindingLimit 错误，不返回部分通过结论。
- 环境版本门禁：SDK 激活脚本按语义版本检查，兼容后续更高主／次版本；不修改全局 PATH、TEMP 或已有 SDK。

## 独立证据

- TFLM 未修改的 GreedyMemoryPlanner 实测：复用 64 字节、交接 128 字节、单 arena 的并存双缓冲 256 字节。使用最小 ABI/日志构建适配，未运行完整 TFLM 推理运行时。
- 本项目对应容量结果与成熟算法一致；跨 bank 案例总物理量仍为 256 字节，区别是允许集合、逐区容量和固定位置共同受到核验。
- C replay 使用 CLI 实际生成的头文件，在真实数组读写中检查四个时间步的数据保持。
- 2048 个缓冲区的合成上限场景通过，实测高水位 49280 字节，本机约 0.307 秒；单机耗时不是性能承诺。
- 发布包清单排除了 .git、.tools、.mooncakes、_build、artifacts；没有凭据、参考源码、缓存或本地编译产物。

机器可读结果见 [verification.json](verification.json)。源码有效行约 1311：实现 848、测试 463，共 10 个 .mbt 文件；不计注释、空行、依赖和生成接口。低于技能中的 4k 正向参考规模，不以填充代码补足，也不把行数视为验收结论。

## 仍需如实保留的限制

1. 公开检索和更新后的 Mooncakes 索引未找到直接同范围项目，不能证明未公开作品不存在。算法及单 arena 复用已有成熟工作，不能宣称算法首创。
2. 尚无真实模型的全量 scratch／持久占用采集、硬件接入和第三方采用证据。新增能力的必要性、生态价值和赛事差异化仍需组委会判断，这是申报风险，不能用单元测试替代。
3. 贪心计划不保证最优；超预算不等于不可行证明。输入清单遗漏占用时，工具无法自动知道遗漏内容。
4. 当前不读取 ONNX/TFLite 模型，不做并行调度、原地别名、缓存一致性或算子正确性验证。完整兼容目标限定为本仓库 SPEC.md 中的 schema 1，不对其他标准作完整兼容承诺。
5. 十一月完整官方网页与实际报名条款未核实；按用户通知沿用十月工程要求。此报告不处理报名状态，也不声称已通过赛事初审或终审。
